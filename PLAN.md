# quest-app — план портфолио-проекта

Источник вдохновения: вакансия Fullstack Developer, Sakura Games (hh.ru/vacancy/134915047) —
не релевантна по опыту/стеку напрямую, но паттерн задачи ("интерактивный квест": лендинг →
выбор пути → сценарий → задания → экран завершения → лидерборд) хорош как пет-проект под
похожие игровые/эдтех full-stack вакансии.

## Формат работы

Пишу код сам. Claude — ревью и контроль на каждом чекпойнте, не пишет продакшн-код за меня.

## Стек

- Next.js (App Router) + TypeScript — фронт и бэкенд (API routes) в одном приложении,
  один деплой, меньше инфры
- Postgres (Neon/Supabase, free tier) + Prisma как ORM
- Деплой: Vercel

## Скоуп MVP (сознательно НЕ делаем на первой итерации)

- Один сценарий/квест, без ветвления путей — экран "выбор пути" не нужен
- Без сюжетной обёртки/сторителлинга — прямое название "JS/TS Quest", без вымышленного контекста
- Анонимные сессии (uuid/cookie), без полноценной авторизации
- Простой лидерборд, без аналитики (PostHog/GA — опционально потом)
- Без Fluent UI, Azure, Cypress — не нужны для портфолио-версии

## Флоу экранов (упрощённый, без пути и сюжета)

Лендинг → Задание 1..N (по одному, с прогресс-баром) → Экран результата → Лидерборд

## Контент MVP — 7 заданий (JS/TS quiz)

1. `typeof null` → `"object"`
2. `0.1 + 0.2 === 0.3` → `false`
3. `[] + []` → `""`
4. hoisting: `console.log(a); var a = 5;` внутри функции → `undefined`
5. `let` vs `var` в цикле с `setTimeout` — классика на замыкания/block scope
6. `interface` vs `type` — declaration merging возможен только у `interface`
7. `unknown` vs `any` — вызвать метод без проверки типа можно только на `any`

Формат вопроса: текст/код-сниппет + варианты ответа (multiple choice), сервер хранит
правильный ответ и начисляет очки (не доверяем фронту).

## Чекпойнты

### 0. Скоуп и архитектура
Список экранов + флоу между ними, что НЕ делаем. Ревью до начала кода.

### 1. Data model
Prisma-схема: сессия, сценарий, задание, попытка/прогресс, очки, запись лидерборда.
Ревью схемы — нормализация, целостность данных.

### 2. Backend API
Эндпоинты: создать сессию → получить сценарий/задания → сабмит ответа (счёт считается
на сервере!) → получить прогресс → получить лидерборд.
Ревью: валидация, edge cases (повторный сабмит, невалидный task id и т.п.).

### 3. Фронт: экраны
Лендинг, интро сценария, экран задания, экран завершения — вёрстка и роутинг, без
реальных данных. Ревью структуры компонентов и стейта.

### 4. Интеграция фронт+бэк
Реальные запросы, состояние прогресса, loading/error states. Ревью data-fetching
паттернов.

### 5. Лидерборд + защита от читерства
Экран лидерборда на реальных данных, server-side валидация от накрутки очков.

### 6. Деплой
Vercel + Neon/Supabase, env vars, миграции в проде, смоук-тест руками.

## Опционально (если останется время)

- Простая аналитика (PostHog free tier)
- E2E-тест на ключевой флоу через Playwright
- Полировка UI
